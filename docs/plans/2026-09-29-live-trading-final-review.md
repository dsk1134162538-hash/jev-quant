## Critical

### C-1 收盘前约 1 分钟内的买单，检查时算「来得及撤」，实际撤不了：单子进收盘集合竞价或跨午休，并触发自动暂停
- **位置**：`jevq/live/executor.py:115`（`_can_cancel_by(now + LIVE_BUY_WAIT)` 预检）、`:205`（`_wait_fill`）、`:279`（`_poll_fill` 截止时间只按 `wait` 算）、`:300-302`（到点撤不了 → 自动暂停）
- **问题**：预检假设「现在 + 30 秒」就开始撤单，下单前那几次读取的耗时都没算进去：读持仓约 6.4 秒、读资金约 2.2 秒、下单约 6.5 秒；轮询还会超出截止时间最多一个周期（sleep 5 秒 + 读 5.8 秒）。实际开始撤单的时间约是「现在 + 47 秒」，`LIVE_ORDER_MARGIN` 的 20 秒不够抵这段差。
- **时间线**（`sim_timing.py`，假券商按网关实测耗时）：超跌反弹偏弱情绪时只在 14:50–14:57 尾盘买。
  1. 14:56:00 模拟盘成交，live.py 在 14:56:00–14:56:09 之间处理这条意图，预检通过（14:56:30 + 20 秒 < 14:57）。
  2. 14:56:47 轮询结束，此时已来不及撤单 → `_auto_pause("来不及撤单…请在 App 里处理")`。这时委托行状态是 `submitted`，意图记为「结果不明」。
  3. 这笔买单进入收盘集合竞价。集合竞价期间交易所不接受撤单，用户在 App 里其实处理不了。限价是模拟价 +0.5%，大概率在收盘成交。
  4. 如果用户第二天早上才点恢复，这行已经是昨天的，按 I-2 的机制，这笔成交永远不会进 `live_positions`。结果：程序不管这 2 万的仓位，模拟盘卖出时也不跟卖；因为 `live_positions` 为空，下一次模拟买入信号还会再买一笔，突破「单只 2 万 / 最多 1 只」的上限。
  5. 如果当天收盘后恢复，而这笔没成交，`_reconcile_open_order_row` 会再走一次 `_cancel_and_confirm`，15:00 以后撤不了，于是又自动暂停。当天点多少次恢复都会重新暂停。

  上午也一样：11:28:52–11:29:10 之间处理的买单会跨午休挂到 13:00。
  实测结果：14:55:45 处理的意图正常撤单；14:56:00、14:56:05、14:56:09 三个时刻全部 `submitted`、没撤单、自动暂停。
- **为什么是 Critical**：超跌反弹尾盘买入是常态，模拟盘在 14:55 或 14:56 那一分钟成交并不罕见；这个窗口约 18 秒，每个尾盘买入日都会碰到。
- **改法**：
  1. `_poll_fill` 的截止时间取 `min(开始 + wait, 最晚还能撤单的时刻 − LIVE_POLL − 一次读取耗时)`，保证撤单一定在连续竞价内发出。
  2. `place()` 之前用新的时钟再检查一次 `_can_cancel_by(clock() + wait)`，不通过就 skipped。
  3. 另外补一个买单的收盘后结算：15:01 以后 open 的买单直接按最终状态落账，和卖单结算一样，不再尝试撤单。

## Important

### I-1 `step()` 抛任何异常，live.py 只记日志：`place()` 之后抛异常会留下没人跟踪、也不报警的真实委托
- **位置**：`live.py:119-122`；`jevq/live/executor.py:204`（`place` 之后的 `update_order(submitted)`）、`:577`（卖单同理）
- **时间线**（`sim_exc.py`）：
  1. `place()` 成功，紧接着写库抛了异常。触发来源比如 I-3 的线程竞争，或者别的进程占着写锁（`database is locked`）。
  2. 意图此前已经标成 `done` 下单中，委托行停在 `sending`。
  3. 实测结果：客户端里买进了 1900 股，`live_positions` 为空，没有暂停，一条通知都没发，只有 `data/live.log` 里一行日志。
  4. 这之后没有任何代码再回头看这一行，只有下次重启或恢复时才会核对。在那之前，因为 `live_positions` 为空、`buys_today` 也不算 `sending`，程序还可以再买别的票。
  5. 另一种情况：如果每一轮都在同一个地方抛异常，心跳在 `step` 开头已经写了，看门狗认为进程正常，于是整天不卖、不报警。
- **改法**：live.py 捕获异常以后，调用 `executor._auto_pause(f"执行异常：{e!r}")`（外面再包一层 try），并发通知。这正好是 spec「意料之外的情况一律自动暂停」的要求；恢复时会走 sending 核对。

### I-2 前一天没核对完的买单（sending/submitted），恢复和启动都只看当天的行；对账只会减不会加：已成交的仓位永远丢了
- **位置**：`jevq/live/executor.py:830-831`（`r["ts"][:10] == today`）、`:750-788`（`_reconcile` 只减账）、`:609-631`（收盘结算只处理卖单）
- **时间线**：
  1. 14:52 买入，网关返回 `TASK_TIMEOUT`，触发自动暂停「下单结果不明…恢复前请在 App 里核对」。
  2. 用户晚上在 App 里看到已经成交，第二天 09:00 点恢复。
  3. `_after_resume` 只核对今天的行，查不到任何东西。账本里这只票不存在，程序把它当成用户自己的仓位，永远不卖。
  4. 同一类问题还会从 C-1、I-1 触发，或者在「下单之后进程崩溃、当天没有被拉起来」时触发。
  5. 进度账本里的 Ruling 写的是「更早的行交给持仓对账」，但对账只会在客户端比程序少的时候减账，这条兜底对买单不成立。
- **改法**：
  1. 实现 C-1 里说的买单收盘结算，并允许收盘后恢复时把这类行直接按最终状态落账，不再尝试撤单。
  2. 启动或恢复时如果发现更早日期的买单行还是 `sending`/`submitted`，发一条醒目的报警，写清楚「昨天 X 的买单没核对，程序不会管这只；如已成交请……」，不能静默跳过。

### I-3 页面线程和执行器共用同一个 sqlite 连接：并发写会直接报错，`pause` 单次提交也起不到隔离作用
- **位置**：`live.py:112`（`make_handler_fn(lambda: conn, …)`）、`jevq/live/web.py:141-160`、`jevq/db.py:67`（`check_same_thread=False`）
- **证据**（`race.py`，Python 3.12 / SQLite 3.45，`threadsafety=3`）：两个线程在同一个连接上同时写，出现了几百次 `OperationalError: cannot start a transaction within a transaction`、`InterfaceError: bad parameter or other API misuse`、`SystemError: error return without exception set`、`cannot commit - no transaction is active`。只读和写并发（`race2.py`）没有出错。
- **会怎样出事**：用户在手机上点暂停、恢复、立即卖出时，执行器正好在写库（下单前后连续写好几次）。
  1. 异常可能落在执行器线程里，比如 `place()` 之后的 `update_order`，那就直接变成 I-1 的场景。
  2. 也可能落在页面线程里：请求报错，但已经写进去一半的暂停键（比如只写了 `paused=1`、没写 `kind`）会被执行器下一次 commit 一起提交，留下一个「kind 为 None、永远不会到点恢复」的暂停。
  3. 另外，`/api/pause` 的「先检查不是自动暂停，再写入」不是原子操作，执行器正好在这中间自动暂停的话，会被页面覆盖成会到点恢复的手动暂停。
  4. 用户双击时，两个请求线程之间也会互相竞争。
- **概率**：低，但每次写库都有可能碰上，而且没有任何兜底。
- **改法**：页面每个请求自己开一个连接，用完关掉（WAL 下各连接互不干扰）。`/api/pause` 的检查和写入放在同一个 `BEGIN IMMEDIATE` 事务里。

### I-4 从「演练」先切「关闭」再切「实盘」，演练留下的假持仓不会被清掉；实盘会把它当真，可能卖掉用户自己的股票
- **位置**：`jevq/live/store.py:62-73`（只在 `dryrun → live` 这一种切换时清空）
- **时间线**：
  1. 10-12 演练收盘时，`live_positions` 里有一只演练买的 X。用户当晚切到「关闭」（比如等客户经理回复报备问题），10-13 再切「实盘」，X 没有被清掉。
  2. 如果用户账户里恰好也有 X，比如演练期间看到模拟盘的推送自己手动买了：对账认为客户端股数 ≥ 程序账，属于正常；模拟盘卖出 X 时，程序会卖掉 `min(假持仓, 可用)` 股，也就是用户自己的股票。
  3. 就算用户没有 X：09:30–09:35 这两次对账把假持仓减掉之前，买入会被「程序已有持仓」挡掉；减账时还会发一条误导性的「按客户端减账（人工卖出）」通知。
  4. 反过来从「实盘」切到「演练」：演练的卖出会用 `reduce_position` 把真实持仓从账本上减掉，再切回实盘时又被整体清空，真实仓位就没人管了；演练模式下 `startup` 对当天遗留的实盘 submitted 行还可能调 `cancel_last`。
- **改法**：离开 `dryrun` 时（切到 off 或 live 都算）清空 `live_positions` 和 `reduce:*`；`live_positions` 不为空时拒绝 `live → dryrun`。

### I-5 卖单只要被留到连续竞价之外（上午临近午休、或下单中途重启），之后就只跟踪、不再改价，一直挂到 15:01 作废
这一条是 deferred minor「上午被慢网关留下的卖单下午只跟踪不改价」，结论是：现在就修。
- **位置**：`jevq/live/executor.py:456-460`（上午预检只算 `LIVE_SELL_WAIT`）、`:521-525`（撤不了就留着）、`:440-443`（`_follow_open_sells` 碰到 open 的行只记录成交、然后等下次重试）、`:860-862`（启动时遇到 open 的卖单也不撤）
- **时间线**：
  1. `sim_timing.py` 用正常的网关耗时就能复现，不需要网关变慢：11:29:15 开始的一轮卖出，轮询结束时已经撤不了，单子挂过午休。
  2. 13:00–13:03 期间只下过 1 次单，价格一直停在上午的 9.9，没有重挂。
  3. 如果下午股价跌破这个价格超过 1%，这只止损票整个下午都卖不掉，15:01 作废，拖到第二天。
  4. 同样的情况：卖出等待的 20 秒里 live.py 被看门狗杀掉或崩溃重启，这笔卖单也会一直挂到收盘。
  5. 触发条件：每天上午临近午休时，某一轮卖出正好在 11:29:05–11:29:20 之间开始（止损卖单每分钟重试时，大约十分之一的概率落进这个窗口），或者卖出过程中进程重启。
- **改法**：
  1. 用 C-1 的截止时间封顶，同样覆盖上午的卖单。
  2. `_follow_open_sells` 里，如果挂着的卖单已经超过 `LIVE_SELL_WAIT` 秒、不是跌停排队单、而且现在能撤单，就走 `_cancel_and_confirm`，结算以后继续重挂。

### I-6（若最终选 easytrader）`TradeError` 被当成「券商明确拒单」：单子可能已经报出去了，程序却记成失败，也不做核对
- **位置**：`jevq/live/easytrader_broker.py:57-58`（`TradeError` 映射成 `ORDER_SUBMIT_FAILED`，这个码在 `REJECT_CODES` 里）
- **问题**：easytrader 只要「提示」弹框的内容里不含「成功」两个字，就抛 `TradeError`。有些券商的成功提示并不写「成功」，比如「委托已提交」。
- **时间线**：
  1. 买单其实已经报出去了，但弹框写的是「您的委托已提交」，于是抛 `TradeError`，行记成 `failed`，通知「买入失败」，不暂停，也不查当日委托。
  2. 真实成交以后，仓位没人管，而且还能再买下一笔。
  3. 卖单一侧因为有「可用余额封顶」，不会重复卖。
- **改法**：`TradeError` 映射成一个不在 `REJECT_CODES` 里的码（比如 `TRADE_ERROR`），让执行器按「认不出的错误」处理：先核对当日委托，找不到才记失败并自动暂停。只用网关的话，这一条可以不管。

## Minor

1. **看门狗按 PID 杀进程，没考虑 PID 被复用**：`jevq/live/watchdog.py:49-51`。live.py 退出以后，Windows 很快会把这个 PID 分给别的进程，心跳超时时就会 `taskkill /F` 一个无关的进程。改法：先确认 `data/live.lock` 还被占着（`runlock.is_held`），或者核对进程的命令行里有 `live.py`，再杀。
2. **看门狗线程的 `db.connect` 在 try 外面**（deferred）：`daemon.py:92`。这一步抛异常的话，看门狗线程当天就静默死掉了，没有报警。改法：挪进循环里，失败就记日志，60 秒后重试。
3. **手机页没校验 Host，可以被 DNS rebinding**：`jevq/live/web.py:121-124`。攻击网页把自己的域名解析到本机或 Tailscale 地址以后，Origin 和 Host 一致，检查形同虚设，就能调 `/api/sell_all`、`/api/resume`。在本机浏览器里连 `/api/mode` 都能改。门槛高，但修起来很便宜：Host 只允许 `127.0.0.1:8766`、`localhost:8766`、`<JEVQ_LIVE_HOST>:8766` 这几个。
4. **「恢复」请求可能提前吃掉之后才发生的自动暂停**：`jevq/live/executor.py:638-642`。时间线：10:30:00 手动暂停到点、自动恢复；10:30:01 恢复后的核对发现不对，触发自动暂停；10:30:02 用户照着 10 秒前页面上的「暂停中」点了恢复，于是这个用户根本没看到的自动暂停被直接清掉了。改法：`resume_requested` 里带上点恢复时所见暂停的原因或时间，和当前暂停对不上就忽略。
5. **零股会一直挡住新的买入**：`jevq/live/executor.py:491-495` 配合 `:121-123`。部分成交留下的零股卖不掉（下单层只收 100 的倍数），在用户手动卖掉之前，「程序已有持仓」会跳过所有买入信号，每分钟还要读一次持仓（网关读一次约 6 秒）。可以接受，但通知里最好说明「在手动卖掉之前不会再跟买」。
6. **自我重启每天只检查一次**：`live.py:126-127`。改了代码以后，deploy 要先在 worktree 里跑一遍测试（最多 15 分钟），rebase 经常晚于 15:10。结果是 live.py 在 15:10 按当天的数据提交重启了一次，却错过了真正的代码更新，新代码要到第二天 15:10 才生效，这一整天 daemon 跑新代码、live.py 跑旧代码。改法：15:10–16:00 之间每 5 分钟检查一次，或者像 daemon 那样只比较 `CODE_PATHS`。
7. **daemon 挂了，live.py 会静默停工**：`jevq/live/executor.py:66-68`。`trading_day` 只由 daemon 写，daemon 没跑的话，live.py 每天都当作非交易日：不卖，也不发 09:05 自检（而看门狗本身也在 daemon 里）。改法：工作日 09:10 如果 `trading_day` 还不是今天，发一条通知。
8. **home_install**：
   - `scripts/home_install.py:105-106`：交易时段只算到 15:05，但 daemon 在 15:05–15:20 做同步、deploy（git rebase 和 push）。这时运行安装脚本，会在同一个仓库里并发 `git fetch/rebase`，接着 `stop_old` 还可能杀掉正在 rebase 的 daemon。建议把结束时间放到 15:30。
   - `:96-102`：`check_env` 不报 `XIADAN_GATEWAY_TOKEN`、`JEVQ_LIVE_HOST` 有没有设置（只说有没有就行）。
   - 已确认：不会覆盖已有数据库，凭证不会打印出来。
9. **live_probe 的 order-test**：
   - `scripts/live_probe.py:106-109`：时段在 `input()` 之前就检查了，用户在 yes 提示前拖过 14:57 或 11:30，照样会下单。
   - `:135-137`：下单返回超时一类的错误时，脚本直接退出，没有提醒「单子可能已经报出去了，去 App 里核对并撤单」。
   - `:164-168`：撤单后在当日委托里找不到这笔（`after is None`），也打印 PASS。
   - 安全闸其余部分都没问题：`--i-understand`、键盘输入 yes、只挂跌停价 100 股、撤单后再读一次确认。

## 待确认（家里实测，交易时段）

1. **撤单接口的 `type:"L"` 真的被网关读到了吗？「撤最后」到底撤哪一笔？**（`gateway.py:73`）
   现在的 order-test 只挂一笔单，「撤最后」和「全部撤单」得到的结果一模一样，分不出来。
   做法：先后挂两笔跌停价 100 股的买单 A、B，调 `cancel_last()`，再读当日委托。必须是 B 已撤、A 还挂着，最后在 App 里手动撤掉 A。如果 A 也被撤了，说明网关没读到 JSON 里的 type，按「全部撤单」执行了，一上实盘就会把用户自己的挂单一起撤掉，绝对不能开实盘。
   easytrader 的 `cancel_entrust` 是按像素行定位的，也要做同样的两笔测试。
2. **客户端「股票余额」包不包括当天买入的股数？**（`executor.py:771-788`）
   如果不包括，程序每次真实买入以后，5–10 分钟内的两次对账会把整个仓位按「人工卖出」减掉，仓位就丢了。演练模式对账不改账，也发现不了。
   做法：交易时段手动买 100 股任意一只票，跑 `live_probe.py read`，看这一只的「股数」列有没有包含刚买的股数。
   不管测出来是什么，都建议现在加一道保护：`buy_date == 今天` 的持仓不按客户端减账。T+1 当天不可能被卖出，所以当天出现的短少只可能是读数的问题。
3. **委托时间的格式和家里电脑的时钟偏差**（`executor.py:320-326`）
   网关默认 `order.capture_entrust_no=false`，`docs/live-setup.md` 的配置示例里也没有打开它，所以下单拿不到委托号，匹配全靠四要素加「时间 ≥ 下单时刻 − 5 秒」。这就是 deferred 里说的「取最后一条」。
   - 如果电脑时钟比券商快了大约 11 秒以上（卖单）或 17 秒以上（买单），每笔单都会匹配失败：显示「委托状态查不到」然后自动暂停；下单报了认不出的错误时，还会把真实委托记成 `failed`。
   - 如果委托时间是 `9:35:00` 这种不补零的写法，或者 easytrader 按整数读成了 `93500`，时间比较和「最后一笔」的排序都会错。
   做法：`read` 输出里看委托时间的原文格式；order-test 下单那一刻记下电脑时间，和委托时间对比；上线前执行 `w32tm /resync`。建议再在网关配置里试一下 `capture_entrust_no: true`，order-test 会打印委托号，确认它和表里的「合同编号」逐字相同。代码侧建议：第一次匹配到委托以后，把合同编号写回行里，之后只按号跟踪。
4. **当日委托里撤单会不会单独成一行？**（`broker.py:102-108`）
   有些客户端会把撤单列成一行，比如操作列是「撤买」「撤卖」。这种行含「买」或「卖」字，会被解析成一笔四要素完全相同的委托，而没有委托号时匹配取的是最后一条，就可能匹配到撤单那一行。
   做法：order-test 撤单以后跑一次 `read`，看有没有多出这样一行。
